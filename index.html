Preface

Welcome to Logic Building and Problem Solving

Logic Building and Problem Solving (LBPS) is the foundational course for future programmers, software engineers, and information-technology professionals. Before writing a single line of code, a programmer must understand the problem, identify the required inputs and outputs, determine the processing steps, and design a logical solution.

This note integrates classical LBPS theory — the definitions, the properties and building blocks of algorithms, the standard flowchart notation, the pseudocode conventions, the three control structures — with extensive C++ implementations of every concept. Where other courses might illustrate an idea only in pseudocode, this note follows through with a working C++ program, expected output, and a hand-trace of the key values.

How to use this note

For each topic: (1) read the pseudocode, (2) trace it on paper with small inputs, (3) type the C++ code by hand, (4) compile and run it, (5) test edge cases. Programming is a physical skill as much as an intellectual one.

Audience

Beginning students in IT, CS, and Software Engineering.

Language

C++ (with pseudocode for design).

Prerequisites

No prior programming. Basic secondary-school maths.

Duration

15 weeks; 2–3 hours of laboratory practice per week.

For Beginners

A Beginner's Companion

If this is your first programming course, read this section first. It will save you from the most common confusions.

Why beginners find programming hard

You are learning three different things at once:

  1. Thinking like a computer — breaking tasks into tiny, unambiguous steps.
  2. A new language — C++ syntax, keywords, rules.
  3. A new tool — editors, compilers, error messages, terminals.

Any single one is manageable; all three together feels overwhelming. That is normal. Every professional programmer went through exactly this.

Walkthrough — Making tea, as a computer would need it

What a human hears: "Make a cup of tea."

What a computer needs to be told:

1. Get a clean cup.
2. Get a tea bag.
3. Place the tea bag inside the cup.
4. Fill the kettle with water (up to the minimum line).
5. Plug in the kettle.
6. Turn on the kettle.
7. Wait until the water boils.
8. Pour the boiling water into the cup (stop before overflow).
9. Wait 3 minutes.
10. Remove the tea bag.
11. (Optional) Add milk and/or sugar.
12. Serve.

Every step is single-action, unambiguous — the level of detail an algorithm needs.

Three beginner mistakes to avoid

Beginner trap #1

Rushing to the keyboard. Fix: spend at least as much time thinking as typing. Write the algorithm on paper first.

Beginner trap #2

Ignoring error messages. Fix: read the message slowly, fix the first error first, recompile.

Beginner trap #3

Assuming code that runs is correct. Fix: predict the output before running.

Weekly study routine that works

  1. Read the chapter without touching the keyboard.
  2. Re-read worked examples, tracing each step on paper.
  3. Re-type every C++ example by hand (not copy-paste).
  4. Run it. Deliberately break it and observe the error.
  5. Solve at least two exercises from Appendix A without looking at the answer.
  6. Explain the concept out loud to an imaginary classmate.

The Four Tools of Problem Solving — A Complete Walkthrough

Every problem in this course can be solved with the same four tools. They all describe one solution — just in four different formats. Once you can read one and immediately picture the other three, programming stops feeling like three unrelated skills and starts feeling like one.

1. Algorithm

Plain-English numbered steps. Not visual. Not code. Written for humans.

2. Flowchart

A picture of the algorithm using standard shapes and arrows.

3. Pseudocode

A structured, code-like version — but not real code. Still for humans.

4. Program (C++)

The working program that the computer actually compiles and runs.

The correct order

Problem → Algorithm → Flowchart → Pseudocode → C++ → Test.
Design first. Code last. Every professional follows this order — and it will save you hours.

The five worked examples below show the same problem in all four tools. Do not skim — read them side-by-side and notice how every step of the algorithm appears again in the flowchart, in the pseudocode, and finally in the C++ program. That mapping is the skill this course teaches.

Example 1 — Sum of two numbers (sequence)

The problem

Ask the user for two whole numbers, add them, and display the result.

Step 1 — Algorithm

1StartEvery algorithm must begin.
2Read AAsk the user for the first number and store it in a box called A.
3Read BAsk the user for the second number and store it in B.
4SUM ← A + BCompute the total. The arrow “←” means “assign to”.
5Print SUMShow the result on screen.
6StopEvery algorithm must end.

Every oval matches “Start”/“Stop”; every parallelogram matches a Read or Print; every rectangle matches a calculation. Nothing else.

Step 3 — Pseudocode

BEGIN
    READ A
    READ B
    SUM ← A + B
    PRINT SUM
END

BEGIN / END are the boundaries — like the Start/Stop ovals. READ takes user input. The arrow ← means “store the right side into the left”. PRINT writes to the screen. That is the entire language you need.

Step 4 — C++ program

C++#include <iostream>
using namespace std;

int main() {
    int a, b;                              // declare two whole-number boxes
    cout << "Enter first number: ";
    cin  >> a;                             // READ A
    cout << "Enter second number: ";
    cin  >> b;                             // READ B

    int sum = a + b;                       // SUM = A + B
    cout << "Sum = " << sum << '\n';        // PRINT SUM
    return 0;                              // STOP
}

Step 5 — Sample run

Enter first number: 5
Enter second number: 7
Sum = 12
What just happened — line by line
  1. int a, b; → reserves two integer boxes called a and b.
  2. cin >> a; → waits for the user to type a number, then puts it in a.
  3. int sum = a + b; → creates a third box called sum, fills it with a + b.
  4. cout << "Sum = " << sum << '\n'; → prints the label, then the value, then a newline.

Compare this to the algorithm: steps 2–5 of the algorithm appear in the exact same order in the C++ program. Nothing was invented during coding.

Chapter 1

Introduction to Logic Building and Problem Solving

1.1 What is LBPS?

Definition

Logic Building is a technique for finding solutions to a given problem using a systematic, technical, and simple-to-implement methodology. LBPS is the discipline of applying that methodology to real problems.

Features of LBPS

LBPS conceptualises a large project into small modules, generates a systematic flow of problem-solving, and shapes it into a real software product.

Plain English

What is "logic building" really? It is simply the habit of thinking in order. Instead of jumping straight into action, you ask: What do I need? What should happen first? What comes next? What are the possible results?

Everyday example: Getting ready for school in the morning.

  1. Wake up.
  2. Brush teeth.
  3. Take a shower.
  4. Eat breakfast.
  5. Pack your bag.
  6. Go to school.

Notice: if you skip step 2 and go straight to school, the result is embarrassing. If you do step 6 before step 1, it's impossible. The order and the completeness are what make this work. That's exactly what a computer needs from you.

1.2 Beginner analogies

Analogy #1 — Blueprint before house

You do not build a house by placing bricks randomly. You first prepare a blueprint. A programmer develops the logic and design before implementing.

Analogy #2 — Recipe

A recipe has inputs (ingredients), a process (steps), an output (dish). Order matters — you cannot fry rice before it exists.

Analogy #3 — Bank queue

First to arrive, first served. Systematic, unambiguous, applied consistently.

1.3 What is problem solving?

Definition

Problem solving is the systematic approach to define a problem and create a number of solutions. It starts with problem specifications and ends with a correct program.

The tools of logic building and problem solving are:

  • Algorithm
  • Flowchart
  • Pseudocode
  • Program (C++)

Seven-step problem-solving cycle:

  1. Identify the problem.
  2. Understand the requirements.
  3. Determine the inputs and expected outputs.
  4. Design the solution.
  5. Test the solution.
  6. Implement the solution.
  7. Evaluate and improve it.

Chapter 2

Fundamentals of Algorithms

2.1 Historical origin

Quoted source

According to C. S. V. Murthy, the word algorithm derives from the ninth-century Arab mathematician al-Khwarizmi, who developed methods using step-by-step instructions. An algorithm is "a step-by-step procedure to solve a given problem". Instructions must be unambiguous and produce a result after a finite number of steps.

Plain English

What makes something an "algorithm"? Four things — think of the acronym F.U.D.I.:

  • Finite — it must end (never run forever).
  • Unambiguous — each step has only one meaning.
  • Deterministic — same input, same output, every time.
  • Input/Output — it needs data in, and it produces a result out.

Everyday algorithm example — Finding your keys in the morning:

1. Look on the kitchen counter.
2. If not there, look on the bedroom nightstand.
3. If not there, look in the bathroom.
4. If not there, look in your bag.
5. If still not there, ask whoever borrowed them.
6. If keys found, STOP. Otherwise go back to step 1 and search again.
7. STOP when keys are found or when you decide to leave without them.

This is finite (you stop when you find them or give up), unambiguous (each step is a clear action), deterministic (following the same steps gives the same outcome), and has input (your starting location) and output (the keys, or a "not found" state).

2.2 General properties of an algorithm

  • Written in simple English.
  • Every instruction precise and unambiguous.
  • No infinitely repeated instructions.
  • Concludes after a finite number of steps.
  • Has an end point.
  • Finite number of instructions.
  • You must know how to solve the problem first.
  • Follows a logical path — order matters.
  • Derived results obtained only after termination.
  • Translatable into a programming language.

2.5.2 States

An algorithm is a deterministic automation: given an initial state, it terminates in a defined end-state. Every algorithm has a start state and an end state.

2.5.3 Control flow

Three types of control flow:

Sequential — top to bottom:

C++#include <iostream>
using namespace std;
int main() {
    int a, b;
    cout << "a b: "; cin >> a >> b;
    int sum = a + b;
    cout << "Sum = " << sum << '\n';
    return 0;
}

Selection — choose between two paths:

C++#include <iostream>
using namespace std;
int main() {
    int a, b;
    cout << "a b: "; cin >> a >> b;
    if (a > b)
        cout << a << " is greater\n";
    else
        cout << b << " is greater\n";
    return 0;
}

Test: a=7, b=3 → "7 is greater". a=2, b=9 → "9 is greater".

Repetition — repeat until condition met:

C++#include <iostream>
using namespace std;
int main() {
    int n;
    cout << "n: "; cin >> n;
    for (int i = 1; i <= n; ++i) {
        cout << i << ' ';
    }
    cout << '\n';

int findMax(const vector<int>& a, int start, int end) {

    int mid = (start + end) / 2;
    int lm = findMax(a, start, mid);
    int rm = findMax(a, mid + 1, end);
    return lm > rm ? lm : rm;
}

}

3.5 Flowchart structures

Sequence Structure

Actions in order — one after another.

Selection Structure (If–Then–Else)

One set of actions if true, another if false. After either branch, control resumes at the next statement.

Repeats a group of steps until some condition is reached. Three parts:

  1. Loop termination decision — when does the loop stop?
  2. Body — what repeats? Must include an action that affects the termination.
  3. Transfer back to the beginning — return to the top.

Pseudocode and Structured English

4.1 Definition

Definition

Pseudocode is a generic way of describing an algorithm without using the syntax of any specific programming language. It is an informal high-level description intended for human reading. The word "pseudo" means imitation. It is also called Program Design Language (PDL).

4.2 Basic rules

  • One statement per line.
  • Each statement is a single action.
  • All inputs on one line if practical.
  • Initial keywords capitalized (READ, IF, WHILE, etc.).
  • Close every structure (ENDIF, ENDWHILE).
  • Language-independent — do not use C++ syntax.

4.3 Example: Find the greater of two numbers

    READ a, b
    IF a > b THEN
        PRINT "a is greater"
    ELSE IF b > a THEN
        PRINT "b is greater"
    ELSE
        PRINT "Both numbers are equal"
    ENDIF
END

C++#include <iostream>

    int a, b;

    if (a > b)       cout << "a is greater\n";
    else if (b > a)  cout << "b is greater\n";
    else             cout << "Both numbers are equal\n";
    return 0;
}

Tests: (10,4) → "a is greater"; (4,10) → "b is greater"; (7,7) → "Both numbers are equal".

Plain English — Choosing the right data type

Think of a data type as a box shape. Each shape fits different contents:

  • int — a shoebox for whole things: your age (21), number of siblings (3), population of a town. Never 21.5.
  • double — a measuring cup: money (₦1,250.75), temperature (36.6°C), a person's height (1.72 m).
  • char — a single-letter slot: a grade 'A', a letter 'x', a symbol '@'.
  • string — a text slot (like a label): a name "Emmanuel", a city "Monrovia", a password "abc123!".
  • bool — a light switch: on or off, true or false. Used for "is the student registered?" or "did the user click Login?".

Choosing wrong is a common bug. If you use int for money and the price is 12.50, C++ stores 12 and you lose 50 cents. If you use double for an age, you get unnecessary decimals. Rule of thumb: whole counts → int, measurements & money → double, letters → char/string, on/off → bool.

Algorithmic Problem-Solving Strategies

7.1 Algorithmic problem solving

Solving problems that require an algorithm. Steps:

  1. Understand the problem — specify the exact input set.
  2. Ascertain device capabilities (e.g. sequential execution).
  3. Decide exact vs approximate solving.
  4. Choose a strategy (brute force, greedy, divide & conquer, ...).
  5. Specify the algorithm (pseudocode or flowchart).
  6. Prove correctness (mathematical induction, loop invariants).
  7. Analyse efficiency (time, space) and simplicity.
  8. Code and test.

7.2 Strategy — Brute force

Try all possibilities until the answer is found. Simple; potentially slow.

Example: find whether a target exists in an unsorted array (linear search).

C++#include <iostream>
#include <vector>
using namespace std;

bool contains(const vector<int>& a, int target) {
    for (int v : a) if (v == target) return true;
    return false;
}

int main() {
    vector<int> a = {10, 5, 25, 8, 60};
    cout << (contains(a, 25) ? "found\n" : "not found\n");  // found
    cout << (contains(a, 99) ? "found\n" : "not found\n");  // not found
    return 0;
}

7.3 Strategy — Greedy

Pick the best local option at each step. Not always globally optimal.

Example: coin change with denominations {25, 10, 5, 1}.

C++#include <iostream>
using namespace std;

int main() {
    int amount; cout << "Amount in cents: "; cin >> amount;
    int coins[] = {25, 10, 5, 1};
    int totalCoins = 0;
    for (int c : coins) {
        int n = amount / c;
        totalCoins += n;
        amount %= c;
        if (n > 0) cout << n << " x " << c << "-cent\n";
    }
    cout << "Total coins: " << totalCoins << '\n';
    return 0;
}

Test: 87 → 3×25, 1×10, 0×5, 2×1 = 6 coins.

7.5 Strategy — Backtracking

Explore a path; undo and try another when stuck.

Example: print all subsets of a set (subset-sum style).

C++#include <iostream>
#include <vector>
using namespace std;

void subsets(const vector<int>& a, int i, vector<int>& cur) {
    if (i == (int)a.size()) {
        cout << "{ ";
        for (int v : cur) cout << v << ' ';
        cout << "}\n";
        return;
    }
    subsets(a, i+1, cur);              // skip a[i]
    cur.push_back(a[i]);
    subsets(a, i+1, cur);              // take a[i]
    cur.pop_back();
}

int main() {
    vector<int> a = {1, 2, 3};
    vector<int> cur;
    subsets(a, 0, cur);
    return 0;
}

7.6 Strategy — Dynamic programming

Cache results of subproblems.

Example: iterative Fibonacci with memoisation in a vector.

C++#include <iostream>
#include <vector>
using namespace std;

int main() {
    int n; cout << "n: "; cin >> n;
    vector<long long> f(n+1, 0);
    if (n >= 0) f[0] = 0;
    if (n >= 1) f[1] = 1;
    for (int i = 2; i <= n; ++i) f[i] = f[i-1] + f[i-2];
    cout << "Fib(" << n << ") = " << f[n] << '\n';
    return 0;
}

Test: n = 10 → Fib(10) = 55.

  • Try to show the algorithm works for every legitimate input.
  • Mathematical induction often works — iterations form a natural sequence.
  • Tracing specific inputs is useful but cannot prove correctness.
  • To prove incorrectness, one counterexample suffices.

7.8 Analysing an algorithm

  • Efficiency — time and space.
  • Simplicity — simpler = easier, fewer bugs.

8.5 Recursion

Definition

Recursion is when a function calls itself repeatedly until some specified condition has been satisfied. Three requirements: base case, progress toward base case, recursive step.

Analogy — Russian nesting dolls

Open a doll → smaller doll inside. Keep opening smaller dolls until you reach the smallest one (base case). Each opening is a recursive step.

Plain English — Recursion without the headache

Imagine you're standing in a long queue and you want to know how many people are ahead of you. You could count them all yourself — that's iteration. Or you could do this:

  1. Ask the person immediately in front of you: "How many people are ahead of you?"
  2. They ask the person in front of them the same question, and so on, until the very front person says "zero."
  3. Each person then adds 1 to what they were told, and passes the answer back.

The key insight: each person solves exactly the same tiny problem ("ask the person in front"), and the "base case" is the person at the very front (nobody is ahead of them). If nobody is at the front — or the front person never answers "zero" — the whole process would never stop. That's why every recursive function needs a base case and progress toward it.

Translating back to C++: factorial(n) says "I need n × whatever factorial(n-1) gives me." The base case is factorial(1) = 1. Each call reduces n by 1, so eventually we hit the base case and all the answers multiply back up.

Factorial — iterative C++

C++#include <iostream>
using namespace std;

long long factorialIter(int n) {
    long long result = 1;
    for (int i = 2; i <= n; ++i) result *= i;
    return result;
}

int main() {
    int n; cout << "n: "; cin >> n;
    cout << n << "! = " << factorialIter(n) << '\n';
    return 0;
}

Factorial — recursive C++

C++#include <iostream>
using namespace std;

long long factorial(int n) {
    if (n < 0) return -1;              // invalid
    if (n == 0 || n == 1) return 1;    // base case
    return n * factorial(n - 1);       // recursive step
}

int main() {
    int n; cout << "n: "; cin >> n;
    cout << n << "! = " << factorial(n) << '\n';
    return 0;
}

17.1 What is an array?

An indexed collection of elements.

C++int a[] = {10, 5, 25, 8};

Plain English — Arrays in real life

Think of an array as a row of numbered lockers in a school hallway. Each locker has a number (the index) and holds exactly one item (the element). All lockers are the same size and next to each other.

  • Locker 0 holds 10 — the first locker.
  • Locker 1 holds 5 — the second locker.
  • Locker 2 holds 25, and so on.

If you want the third item, you say "locker 2" — not "locker 3". This is why arrays start at 0.

Real-world arrays in the wild:

  • Your phone contacts list — a row of names, each with an index from 0 upward.
  • Test scores of 30 students in a class — scores[0] through scores[29].
  • Days of the week — days[0] = "Monday" (or Sunday, depending on your convention).
  • Seats in a cinema — row 5, seat 12. The index pair uniquely identifies a spot.

Why not just use 30 separate variables? Because a loop can walk an array in one line: for (int i = 0; i < 30; ++i). Thirty variables would need thirty statements.

Off-by-one trap

If an array has n elements, valid indices are 0..n-1. Accessing a[n] is out of bounds.

C++int binarySearch(const vector<int>& a, int target) {
    int lo = 0, hi = (int)a.size() - 1;
    while (lo <= hi) {
        int mid = (lo + hi) / 2;
        if      (a[mid] == target) return mid;
        else if (a[mid] <  target) lo = mid + 1;
        else                       hi = mid - 1;
    }

}

}

    vector<int> L(a.begin()+l, a.begin()+m+1);
    vector<int> R(a.begin()+m+1, a.begin()+r+1);
    int i = 0, j = 0, k = l;
    while (i < (int)L.size() && j < (int)R.size())
        a[k++] = (L[i] <= R[j]) ? L[i++] : R[j++];
    while (i < (int)L.size()) a[k++] = L[i++];
    while (j < (int)R.size()) a[k++] = R[j++];
}

void mergeSort(vector<int>& a, int l, int r) {
    if (l >= r) return;
    int m = (l + r) / 2;
    mergeSort(a, l, m);
    mergeSort(a, m + 1, r);
    merge(a, l, m, r);
}

void bfs(const vector<vector<int>>& g, int start) {
    vector<bool> seen(g.size(), false);
    queue<int> q;
    q.push(start); seen[start] = true;
    while (!q.empty()) {
        int v = q.front(); q.pop();
        cout << v << ' ';
        for (int u : g[v])
            if (!seen[u]) { seen[u] = true; q.push(u); }
    }
    cout << '\n';
}

    for (int u : g[v])
        if (!seen[u]) dfs(g, u, seen);
}

Beginner Pitfalls and Fixes (C++)

#1 — Skipping planning

Fix: write the algorithm on paper first, then code.

#2 — Confusing = and ==

Fix: = stores, == compares.

#3 — Off-by-one in loops/arrays

Fix: arrays use 0..n−1. Trace first and last iterations.

#4 — Forgetting the loop update

Fix: every while must eventually make its condition false.

#5 — Integer-division surprise

Fix: 9 / 2 is 4. Use 9.0 / 2 or (double)9 / 2.

#6 — Missing semicolons / braces

Fix: every statement ends in ;. Braces { } must balance.

#7 — Using an uninitialised variable

Fix: initialize at declaration. Accumulators → 0; products → 1.

#8 — Trusting user input

Fix: check cin with if (!(cin >> x)). Validate ranges.

#9 — Silently swallowing errors

Fix: print helpful messages; log details.

#10 — Copy-pasting code you don't understand

Fix: re-type by hand. Explain every line.

#11 — Testing only happy-path

Fix: test typical, boundary, invalid, empty, and large inputs.

#12 — Using Python syntax in C++

Fix: no print() in C++ — use cout <<. Boolean operators are && / || / !, not and / or / not.
